## MainWindow dead `using` alias cleanup (handoff)

### Background

During the 2.9.0 "Copy Profile To Another Model" refactor, `MainWindow` (all `MainWindow*.cs` partials)
exceeded its hard nonblank-line budget (5233 > 5200). Besides extracting
`CopyLaunchProfileToAnotherModelAsync` into
`src/LocalLlmConsole.App/Ui/Pages/Models/ModelLaunchProfileCopyController.cs`, the line budget was
recovered by deleting **dead `using` alias directives** from a few partials.

A full scan found that most MainWindow partials declare the same 8 aliases (lines 5-12) that are never
referenced in their code body — the bodies use the plain type names (`Button`, `CheckBox`, …), which
already resolve through the ordinary `using System.Windows.Controls;` line. Deleting an unused alias is
compile-time-only and changes nothing at runtime, so it is a zero-behavior-change cleanup.

### What was already done in 2.9.0 (do NOT repeat)

All 8 dead aliases were removed from these three files:

- `src/LocalLlmConsole.App/Ui/Shell/MainWindow/Runtimes/MainWindow.ModelRuntime.cs`
- `src/LocalLlmConsole.App/Ui/Shell/MainWindow/Core/MainWindow.Execution.cs`
- `src/LocalLlmConsole.App/Ui/Shell/MainWindow/Navigation/MainWindow.Logs.cs`

After that, MainWindow is at **5193** nonblank lines (under the 5200 hard limit, still above the 5000
warning threshold). The plan deliberately did not chase below 5000.

### The dead alias block (example)

```csharp
using System.Windows;
using System.Windows.Controls;
using System.Windows.Data;
using System.Windows.Media;
using Forms = System.Windows.Forms;          // <-- unused in these files
using WpfApplication = System.Windows.Application;   // <-- unused
using WpfBinding = System.Windows.Data.Binding;      // <-- unused
using WpfButton = System.Windows.Controls.Button;    // <-- unused
using WpfCheckBox = System.Windows.Controls.CheckBox;// <-- unused
using WpfComboBox = System.Windows.Controls.ComboBox;// <-- unused
using WpfProgressBar = System.Windows.Controls.ProgressBar; // <-- unused
using WpfTextBox = System.Windows.Controls.TextBox;  // <-- unused
```

Why it is dead: the method bodies reference `Button`, `CheckBox`, `ComboBox`, `ProgressBar`, `TextBox`,
`Application`, `Binding`, and `Forms.Screen` directly — they never use the `Wpf*` / `Forms` alias names.
A word-boundary grep for each alias in these files finds only the declaration line itself.

### Safety — how to verify before committing (IMPORTANT)

- An unused `using X = ...;` produces no compiler warning or error, so removing it cannot change
  compilation or behavior. The real types stay resolved via the plain usings.
- The only failure mode is deleting an alias that IS used somewhere in that file — that becomes a compile
  error naming the exact symbol and location.
- Recommended workflow: remove a batch of listed lines, then run `scripts/build-app.ps1 -Restore` (must
  show 0 errors) and `scripts/check-code-shape.ps1`. If the build fails on an alias you removed, that file
  actually used it — restore just that one line.
- These deletions are line-count-only and should be their own focused cleanup PR (issue-per-PR), not mixed
  into a feature change.

### Non-EN locale test failures — FIXED by pinning the culture in the test base

~17 tests asserted en-US number/percent/date formatting (decimal dot) and failed on developer's non-en-US Windows machine (`12,0 GiB`, `50 % (1 KB)`, `0.075 seconds`). All failing classes derive from
`ManagerRegressionTestBase`, so the culture is now pinned there once for every regression test:

```csharp
var usCulture = new CultureInfo("en-US");
Loc.LoadLanguage("en");
System.Threading.Thread.CurrentThread.CurrentCulture = usCulture;
System.Threading.Thread.CurrentThread.CurrentUICulture = usCulture;
```

Why not an environment variable (verified empirically on this machine):

- `DOTNET_SYSTEM_GLOBALIZATION_PREFERCULTURE=en-US` is ignored on Windows — it only applies when the OS
  cannot supply a culture (e.g. Linux without ICU). The failing tests still formatted in the non-English
  locale with it set.
- `DOTNET_SYSTEM_GLOBALIZATION_INVARIANT=1` breaks this codebase: `LocalLlmConsole.Localization.Loc`
  creates named cultures (`CultureInfo.GetCultureInfo("en")`) and throws `CultureNotFoundException` in
  invariant mode, so no test can even construct its base class.

.NET 10 API note: the static accessors `Thread.CurrentCulture` / `Thread.CurrentUICulture` are gone — set
them through the instance (`System.Threading.Thread.CurrentThread.X`). The culture flows across `await`
boundaries (ExecutionContext), so async tests are covered by pinning in the constructor.

Result: full suite is green on this non-en-US machine — **1045/1045 passed, 0 failed** via
`scripts/test-app.ps1`. (`UiAsyncRefreshTimerControllerCoalescesOverlappingTicks` flaked once under a
full-suite run and passes in isolation; treat it as timing-sensitive, not culture-related.)

All gate steps pass on this tree: code shape (MainWindow 5193 ≤ 5200), build 0/0, tests green, formatting
OK, `git diff --check` OK, docs validation exit 0. Note that `scripts/test-release-gate.ps1` itself
requires a clean Git worktree, so run the full gate only after the v2.9.0 changes are committed by the user.
